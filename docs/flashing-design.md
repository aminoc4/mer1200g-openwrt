# 已验证的启动镜像写入原理

这里记录的是一台 MER1200G Ver1.1 的实际验收过程，不是可对任意固件、硬件版本照抄的刷写命令。当前设备已成功启动 OpenWrt initramfs；正式持久化候选尚未实机启动，也没有验证失败启动后的免串口恢复方式。

## 保留原厂引导程序

成功的这次 OpenWrt 安装是在恢复后的原厂系统中，通过 SSH 操作。引导程序继续保存在物理闪存 `0x000000–0x040000`，没有在这次写入中修改。适配镜像放在原厂引导程序加载内核的位置，使用经过检查的 MIPS/Linux/LZMA 单组件 multi-uImage 封装。

这与直接套用其他机型的官方固件不同。镜像中的设备树、内存大小、交换机接口、内核入口和压缩格式都需要单独适配、核对。

## 在 RAM 中接管后再写入

镜像与受限写入程序先上传到 RAM 并核对哈希。运行程序接管系统后，停止旧服务、正常卸载旧文件系统，确认不再从待修改的闪存区域运行程序或访问文件。正常卸载包括等待原来的 JFFS2 活动结束。

本次实际写入范围是 `[0x040000, 0x530000)`：79 个 64KiB 擦除块，共 5,177,344 字节。镜像本身为 5,153,875 字节，末尾对齐块中剩余的 23,469 字节沿用写入前内容。写入程序限定范围、按块擦除、按页写入，并在每个块后校验。

结束前关闭写入描述符，再完整回读目标范围，并逐字节核对范围外数据。此次内核镜像读回一致；bootloader、设备信息、ART 及所有范围外字节均与本次冻结基线一致。随后设备保持在 RAM 等待，由操作者断电重新上电。

## 为什么现在配置不会保存

闪存中已经保存了启动镜像；每次开机由原厂引导程序加载它。该镜像使用 initramfs，运行时根目录是 RAM，所以当前网页组件、配置和临时密码会在断电后丢失。

持久化需要新的根文件系统和独立配置区设计，并验证正常挂载、首次初始化及后续保存流程。它不是在网页中点一次保存就能解决的问题。

## 不能重复使用旧的分区号或写入器

分区号是当前内核的映射，不是永久硬件地址。原厂内核的 `mtd9` 曾映射整片闪存；当前 OpenWrt 中 `mtd9` 是 ART。不得把旧内核命令搬到新内核中运行。

当前验收内核没有启用 kexec 或 `/dev/mem`，且所有 MTD 分区都缺少可写标志。新持久化候选的安装通路仍需独立评审。旧的 79 块写入器不覆盖未来的完整持久化布局，也不能作为通用升级程序。

本仓库不分发个人设备的原厂闪存、bootloader、ART 或配置备份。完整备份应由设备所有者自行离线保管。
